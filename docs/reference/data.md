# 数据目录

每个租户有两个目录，都在 `tenants.json` 里指定：`data`（数据库和派生数据）和 `recordings`（原始录音）。按快速开始部署的 Docker 里，它们是宿主机上的 `data/main` 和 `data/main/recordings`。

## DATA_DIR

`DATA_DIR` 在 Docker 里是宿主机的 `./data`；用 uvx、pip 或从源码运行时默认是用户数据目录（见[配置项](./configuration.md)）。第一次启动生成的租户 `main` 在它下面：

```text
<DATA_DIR>/
├── tenants.json
├── models/                         模型文件（MODELS_DIR）
└── main/                           租户 main 的 data 目录
    ├── live.db                     SQLite 数据库（WAL 模式，旁边有 live.db-wal、live.db-shm）
    ├── <日期>.passes.jsonl          每次转写时引擎的原始输出
    └── recordings/                 租户 main 的 recordings 目录
        └── chunks/<设备名>/<日期>/<HH>.<扩展名>
```

## data 目录

| 路径 | 内容 |
|---|---|
| `live.db` | SQLite 数据库，见下表；结构定义在 [`server/alldayrec/db.py`](https://github.com/suyiiyii/alldayrec/blob/main/server/alldayrec/db.py) |
| `<日期>.passes.jsonl` | 每一遍转写时引擎的原始输出 |
| `owner-redimnet2.npz` | 「我」的声纹 |
| `voices/clips/` | 说话人的声音片段 |
| `firmware/` | 录音设备的固件包（只在第一个租户的目录里） |
| `live-record.apk` | 服务器在 `/app.apk` 提供的安卓 App（只在第一个租户的目录里） |

## recordings 目录

| 路径 | 内容 |
|---|---|
| `chunks/<设备名>/<日期>/<HH>.<扩展名>` | 每台设备每小时一个文件，收到的音频块原样追加在后面；每块在文件里的位置和长度记在 `live.db` 的 `pieces` 表里。扩展名按上传时的 `Content-Type`：`ogg`、`webm`、`aac`，其他是 `bin` |
| `chunks/<设备名>/<日期>/<HH>.trim.<扩展名>` | 修剪过的小时（`trim.py`）：原小时文件里有人说话附近的块，按原样、按顺序拷过来；在对象存储里时是 `s3:` 开头的同名对象 |
| `staging/chunks/<设备名>/<日期>/<HH>.<扩展名>.<代>` | 只在 `STORAGE=s3` 时有：已封存的小时又来的迟到块，合并进对象前先存在这里。这时 `pieces.path` 以 `s3:` 开头的块在对象存储里（`<S3_PREFIX><租户 id>/<路径>`），见[录音存在哪里](../explanation/architecture.md#录音存在哪里) |
| `rejected/<设备名>/<开始时刻>.<扩展名>` | 解码失败（接口返回 400）的上传，原样留着供检查 |

## live.db 的表

| 表 | 内容 |
|---|---|
| `sentences` | 定稿的句子：时间、说话人、文字、来源设备、引擎 |
| `drafts` | 初稿层的句子（只在页面开着时产生），定稿覆盖后仍保留 |
| `conversations` | 对话：起止时间、参与者、说话秒数、句数、设备 |
| `summaries` | 每段对话的摘要（JSON） |
| `timelines` | 对话结束时的实时分析 |
| `voices` | 每段对话里每个说话人标签的声纹和声音片段（片段的起止 `clip_start`、`clip_end`；早期外部生成的历史片段没有，为空，这种片段只在设备的偏移对所有时间是同一个值时才标定，见[设备增益](configuration.md#设备增益-device-gain)） |
| `apart` | 被标成「不是这个人」的声音 |
| `people` | 认出名字的人的声纹 |
| `enrolled` | 每个人的声纹是从哪些句子学来的，一句一行；撤销和拆开时据此减掉 |
| `aliases` | 一个人的别名 |
| `terms` | 热词和术语：每个词和添加或修改的时刻 |
| `name_hints` | 每个标签在对话里被怎么称呼（只用于建议名字） |
| `profiles` | 认出名字的人的人物卡片，每一行带出处 |
| `pieces` | 上传的音频块索引，也是处理队列；`samples` 是块上传时解出来的样本数（16 kHz），v0.5.0 之前的块没有（NULL） |
| `trims` | 修剪过的小时文件（`trim.py`）：原件、保留下来的副本、状态，和修剪前的全部索引行（从备份恢复用） |
| `cold_starts` | 紧挨着的前一块被修剪丢掉的录音豆块：读出来时开头渐入 |
| `late_spans` | 迟到录音的精确区间、处理状态与重试次数（v0.4.0 起有） |
| `processed_audio` | 与定稿句子同事务保存的实际处理覆盖（含停顿）；重启及补转写据此去重（v0.4.0 起有） |
| `seg_emb` | 只在 `tenants.json` 的 `seg_emb` 打开时写：每个定稿识别分段的声纹，一段一行（拆句的每部分各一行、各用自己的起止和向量）：设备、起止毫秒（unix）、拆句后的第几部分（没拆为 0）、引擎给的说话人、模型文件和 sha256 前 12 位、fp16 向量、`gain_db`（这段音频送进模型前乘的标定偏移，单位 dB，`device_gain` 的 `offset_db`，没有登记为 0；一段跨过偏移的生效时刻时记它起点的）、它所在句子在 `sentences` 里的 `rowid`（`sentence`：分段可能互相重叠，两句也可能同一毫秒开始，靠起止时间和句子 id 都分不清归属）、它的引擎分段在这一块里的序号（`seg`，从 0 起）、写入时这句的 `start`（`sentence_start`）；每个 `(sentence, seg, part)` 只有一行，重复写入报错，不覆盖。只跟着写进库里的句子存（被后补层保护而没写进去的句子不存），和它自己的句子（重新定稿）、它的音频（`trim.py` 修剪）一起删；写失败只记日志和计数（设备状态的 `seg_emb_failed`），不影响定稿。一条声纹属于哪句：这句的 `rowid` 等于 `sentence`、设备（`source`）等于 `device`、`start` 等于 `sentence_start`，三条都相等才算（分段的起止说明不了归属：一句可以在它里面某段开始之前就结束）；否则不属于任何句子，重新定稿也不删它，跟它的音频一起被修剪删掉。`rowid` 只在整个库文件原样复制时保证不变（停机打包、SQLite 备份接口）；用 SQL dump 或 `INSERT … SELECT` 重建会重新编号，声纹就成了不属于任何句子的，只有同一台设备上同一毫秒开始的两句之间可能张冠李戴。所以只能按[备份与恢复](../how-to/backup.md#恢复)整库恢复（v0.5.0 起有） |
| `conversation_aliases` | 合并前的对话网址和说话人标签到保留对话的映射（v0.4.0 起有） |
| `walls` | 长对话切开的位置（每台设备一个时刻一行）：迟到音频不会把两边重新合并（v0.5.0 起有） |
| `sounds` | 环境声音的打分（开了[环境声音](./configuration.md#可选-环境声音)才有）：每台设备、每个模型、每段解出来的连续音频一行，见下面的[环境声音](#环境声音-sounds) |
| `sound_wrong` | 声音标签上点的「不对」：设备、起止毫秒、事件、当时用的模型、对话 id（声音条上点的、不在对话里的那一段为空），见下面的[声音事件](#声音事件-sound-events) |
| `feedback` | 用户对摘要的纠正 |
| `todo_marks` | 待办上的「完成」或「不对」标记（v0.2.0 起有） |
| `stars` | 收藏的句子：句子 id、设备、开始时刻、所在对话（只有这次改动前的收藏存了；其余读的时候现查，同上报）、收藏的时刻（v0.3.0 起有） |
| `reports` | 「上报问题」：用户写的问题、上报时刻、来源页面（live 或 conversation）、句子 id、设备、开始时刻、（所在对话不存：读的时候现查这台设备上起止包含这句开始时刻的已结束对话；没有就是对话还在进行，或这句不在任何对话里），以及那一句当时的样子（原文、说话人、起止、初稿或定稿、设备、转写引擎） |
| `mcp_links` | AI 连接网址：名称、密钥的 SHA-256 哈希和前 8 个字符、创建和最近使用的时刻，不存密钥本身（v0.4.0 起有） |
| `kv` | 每台设备的处理进度等键值 |
| `device_log` | 手机上传的设备事件，包括录音设备自己的日志 |
| `device_status` | 客户端读到的录音设备状态（电量、存储卡、固件） |
| `device_gain` | 每台设备的增益，按时间段生效：设备、生效起点（unix 毫秒）、采集增益 `capture_db`（设备上报或手工登记）、标定偏移 `offset_db`（服务器解码后乘，对齐到 −26 dBov；没有记录为 0）、来源（`manual` 手工、`reported` 上报）、备注。标定灵敏度的偏移从 0 开始登记（[设备增益](configuration.md#设备增益-device-gain)）。见[电平和增益](../explanation/architecture.md#电平和增益)（v0.5.0 起有） |
| `calls` | 每次语音识别和大模型调用的耗时、结果和用量，不记内容 |
| `balances` | 预付费账户的余额，每小时一次 |
| `perf_stalls` | 事件循环被卡住的记录：结束时刻、毫秒、卡在哪些函数（只在第一个租户的库里；v0.3.0 起有） |
| `perf_samples` | 进程每分钟一行：CPU 秒、内存、循环延迟、各线程池占用、排队的音频块、打开的网页数（只在第一个租户的库里；v0.3.0 起有） |
| `perf_requests` | HTTP 请求：用时 50 ms 及以上的每个一行，另外每分钟按方法、路由、状态码各一行汇总（v0.3.0 起有） |
| `perf_pieces` | 每个定稿块和初稿轮次各步骤的耗时：解码、VAD、识别、声纹、写库（v0.3.0 起有） |

`perf_` 开头的表只记耗时和资源用量，不记内容，保留 90 天。`GET /api/perf?day=YYYY-MM-DD` 读一天的；从数据库副本导出用 `python -m alldayrec.perf export <live.db> <YYYY-MM-DD>`。

`enrolled` 出现之前学到的声纹，每人只有一行汇总，不对应具体的句子。那时学进了别人声音的，可以用 `python -m alldayrec.bank relearn <live.db>` 从这个人现在名下的声音（实时录音里的）重新算出这一行：只打印每人前后的句数、用上和丢掉的声音数、新旧声纹的余弦，不写库；加 `--apply` 才写，写完重启服务端（声纹在启动时载入）。之后逐句学到的不受影响。用 `relearn --tenant <ID>` 跑、打开了 `BG_GATE` 且这个租户开了环境声音时，只用查得出没有音乐的声音（见[配置项](./configuration.md#可选-环境声音)）。

摘要提示词更新后，已有摘要保持原样，`summaries.prompt_version` 记录各条的版本。部署新版本后，在服务端的 `server/` 目录中回填：

```sh
# LIVE_RECORD_URL 指向本次已确认的实例；LIVE_RECORD_TOKEN 从环境读取，也可从 stdin 第一行输入。
uv run python -m alldayrec.resummarize --days 30 --dry-run
uv run python -m alldayrec.resummarize --days 30 --limit 1
uv run python -m alldayrec.resummarize --days 30 --delay 5
```

范围按运行机器的日历日期，含今天共 N 天，只处理在范围内开始、已结束且说话至少 60 秒的对话；更早、仍进行中、pending 和已在当前提示词版本的跳过。先单段检查，再扩大范围；中断后重跑会跳过已完成的。单段不足 60 秒的「立即总结」保留。每段等待完成后再处理下一段，默认间隔 5 秒，`--max-delay` 默认 600 秒；HTTP 429 和模型 429 都退避。`--timeout` 默认 1800 秒，超时或 HTTP 结果不明时停止，先检查服务端是否仍在处理，再重跑。失败退出码为 1；输出完成、失败、跳过数量，已处理对话的待办与已标记数前后对比，以及期间的模型调用数（含其他后台任务）。

重写期间已成功的旧摘要可见，模型调用失败时仍保留；重试此前失败的摘要时先变成 pending，回填等待本轮结果。待办可在摘要中保存固定 `id`：唯一匹配（内容或原句相同、执行人与接收人相同）的新待办继承旧 ID，完成/不对标记行不迁移、不复制；无法唯一匹配的已标记旧待办原样带入新摘要，保留 ID 和标记，不因标记拒绝整条摘要。其他新任务使用新 ID，避免旧 ID 被另一件事复用。重命名/合并同步更新旧待办的执行人与接收人，撤销按任务 ID 恢复实际改过的字段。重复生成、撤销或重新标记始终操作同一 ID。已有未固定 ID 的摘要仍按引用时间/内容计算原 ID，首次重写时固定下来。收藏保存在 `stars`，重写摘要不改句子或收藏。

已有日回顾不会自动更新；其待办优先按固定 ID 读取当前内容和标记，旧格式按原文字段核对，找不到的只展示文字，避免旧回顾标记到另一件事。回填后建议对受影响且已存在回顾的日期逐日调用 `POST /api/recap/{YYYY-MM-DD}`（`recap_redo`），更新要点与待办引用；每个有摘要的日期额外 1 次模型调用，30 天最多 30 次。100 段通常需要 100 次摘要调用；每段最多尝试 4 次，因此最多 400 次。缺少姓名提示时每段可能再有 1 次 hints，已有档案的具名参与人还会各触发 1 次 profile；租户开了 `place` 时，每段写完摘要再调用 1 次推断地点（主模型失败转备用模型时多 1 次请求）。这些与回顾不包含在 100 次里。实际调用数由脚本的 ledger 统计；金额取决于配置模型和输入长度。

租户开了 `place`（见[配置](./configuration.md#tenants-json)）以后，之前写好的摘要没有地点。只补地点、不重写摘要，在服务端的 `server/` 目录中运行（用实例自己的 `.env` 里的大模型配置）：

```sh
uv run python -m alldayrec.place backfill --tenant <ID> --days 7 --dry-run   # 只打印段数和估算的输入 token
uv run python -m alldayrec.place backfill --tenant <ID> --days 7
```

只处理含今天共 N 天里开始、摘要已调用过大模型、还没有 `place` 的对话，一段接一段（有失败的退出码为 1，重跑接着补剩下的）；只在摘要的 JSON 里加 `place` 一个字段，标题、待办和标记、人物档案都不动。补的时候某段摘要被重写了，这段就跳过，由重写后的摘要自己推断。租户没开 `place` 时直接退出。

## 环境声音 sounds

主键是（`device`、`model`、`start_ms`）。`model` 是模型名加模型文件 sha256 的前 12 位（例如 `mn10_as@58d4c290739e`），换了模型文件就是另一个模型，旧的行原样留着。每一行是一段解出来的连续音频，最长 300 秒：

| 列 | 内容 |
|---|---|
| `start_ms`、`end_ms` | 这段音频的起止（毫秒时间戳） |
| `hop_ms`、`window_ms`、`n` | 帧的间隔、每帧多长、帧数：`mn10_as` 每 10 秒一帧（最后不到 2 秒的并进前一帧），`yamnet` 每 0.48 秒一帧、每帧 0.96 秒 |
| `db` | 每帧的音量，dBFS 取整，一帧一个 int8 |
| `top` | 每帧打分最高的 10 个类别：zlib 压缩的 `n × 10` 个（类别号 uint16，分数 float16）。类别号是 AudioSet 的，按模型自己的顺序（`mn10_as` 527 类，`yamnet` 521 类）。`yamnet` 的这一列 30 天后清空（由开着环境声音的租户的补算循环每小时做一次，回填命令不做） |
| `minutes` | 每分钟一条（按帧的中点归到哪一分钟）：zlib 压缩的（Unix 分钟 int32、帧数 uint16、每个类别的平均分 float16、每个类别 0.2 分及以上的帧数 uint8）。一直保留 |
| `gaps` | 这一行里没有任何块的时间（JSON，`[[起, 止], …]` 毫秒），模型在这里看到的是 0，不算已经算过 |
| `gain_db` | 这一行的输入送进模型前乘的标定偏移（dB，`device_gain` 的 `offset_db`；没有登记为 0）。一段音频跨过偏移的生效时刻，就分成两行，各记各的 |
| `at` | 写入的时刻 |

同一段重算会整行替换。一行只盖解出来的音频：解不开的块、解短的块处断开，不写行，所以没有行的地方就是还没算或者没算成；两块之间不超过 0.5 秒、没有任何块的空档并进同一行，记在 `gaps` 里。算过的范围 = 各行的 `start_ms`–`end_ms` 减去它的 `gaps`（修剪闸门和补算都按这个，精确到毫秒）。一块算不算解全，按样本数和上传时的 `pieces.samples` 精确比，差 1 个样本也不算，这块最后那 1 毫秒就算没覆盖；没有 `samples` 的老块只能按 `seconds`（精确到毫秒）比，解短 1 毫秒以内可能看不出来。之后有块落进 `gaps`，会给它单独写一行，不删原来那行，所以那一分钟的帧可能来自两行。按真实录音估算，一小时录音大约占：`mn10_as` 80 KB，`yamnet` 250 KB（30 天后 60 KB）。

## 声音事件 sound_events

开了环境声音的租户（`SOUND_MODEL` 加上 `"sound": true`），网页和 MCP 从 `sounds` 的打分推出几种声音事件。事件不存表，每次按需从打分算（`sound_events.py`）；用哪个模型的打分由 `SOUND_EVENTS_MODEL` 定（默认 `SOUND_MODEL` 的第一个）。没开时什么都不算、不显示，接口和以前一样。

只出评测里认得准的四种，每分钟一组：

| 事件 | 怎么判（`mn10_as` / `yamnet`） |
|---|---|
| 说话 `speech` | 这一分钟里人声类（Speech 及各种说话、Conversation）的平均分最高的达到 0.3 / 0.2，且这一分钟不是「安静」 |
| 音乐 `music` | 音乐、唱歌、乐器类的平均分最高的达到 0.3 / 0.1 |
| 交通工具上 `vehicle` | 车辆、引擎、交通、铁路、飞机类的平均分最高的达到 0.3 / 0.2，并且连续至少 3 分钟（偶尔路过一辆车不算）。汽车、公交、地铁、飞机分不开 |
| 安静 `quiet` | 这一分钟的音量（各帧平均功率）低于 −55 dBFS（没标定的低于 −60：`gain_db` 为 0，没登记设备增益，或者正好登记成 0 dB），并且没有音乐 |

- 门限是在一组人工标注的 10 秒样本（84 条，标定后，暂定的标注不算）上定的：说话 0.3、去掉安静的分钟时 26 条有人说话的检出 24 条、判出的 40 条里 24 条对（外放的视频、电话也被判成说话）；音乐 0.3 时 13 条检出 12 条、判出 13 条对 12 条；交通工具 0.3 时 4 条检出 3 条、判出 6 条对 3 条，所以另加连续 3 分钟；安静 13/17、判出 16 条对 13 条。样本少，`yamnet` 只是对照，以后用更多数据再定。
- 外放媒体（电视、视频、外放电话）、键盘、脚步、衣服摩擦、风噪、人声嘈杂、底噪、餐具、转向灯认不准，不出。
- 不算的帧：一行里 `gaps` 的部分、音量在 −127 dBFS 的帧（数字静音，麦克风没送来声音）。一分钟没有剩下的帧就是没有数据，不当安静。
- 置信度 `conf`（0–1）：这一分钟里这个类别达到 0.2 分的帧占多少（安静：低于门限的帧占多少）。`yamnet` 的音乐门限 0.1 比 0.2 低，判出音乐的分钟 `conf` 也可能是 0。界面上的事件一律写「可能」。
- 一段对话的声音标签：按对话的设备和起止，统计各事件的分钟数；音乐、交通工具、安静中至少 2 分钟、并且至少占有数据的分钟的 10% 的才列，按分钟数从多到少最多 3 个；安静超过一半写「大半时间安静」。对话两端的那一分钟只要有帧落在对话里，就按整分钟算。说话不做标签。没有设备的旧对话没有标签。
- `GET /api/sounds/day?date=` 给这一天每台设备按分钟连成的段（同样的事件、同一段对话连成一段），没有数据的时间不出现。`GET /api/search?sound=music|vehicle|quiet` 只返回有这个标签的对话；它每次最多看 50 段对话，看完还没凑够 `limit` 段时，响应头 `X-Searched-To` 给出看到哪里，拿它当 `before` 接着搜（网页自己接着搜）；别的取值返回 400。

`sound_wrong`：标签或声音条上点「不对」记下的一行，以后用来扩充人工标注。

| 列 | 内容 |
|---|---|
| `id`、`at` | 编号、点的时刻 |
| `device`、`start_ms`、`end_ms` | 哪台设备的哪一段（对话标签：对话的起止；声音条：那一段） |
| `event` | 哪个事件不对（`speech`、`music`、`vehicle`、`quiet`） |
| `model` | 当时用的模型（名字加文件 sha256 前 12 位） |
| `conv` | 所在对话 id，没有对话时为空 |

一个「不对」管它盖住一半以上的那段时间：对话后来被迟到的音频延长、和别的对话合并，或者声音条重新分段，标签和那一段照样显示「不对」。不分模型：换了模型文件（sha 变了，标签和声音条只用新模型的打分，要等补算）以后照样认。再点一次「撤销」删掉这一行。导出：`GET /api/sounds/wrong`（JSON，按编号排），或 `sqlite3 live.db "SELECT * FROM sound_wrong"`。
