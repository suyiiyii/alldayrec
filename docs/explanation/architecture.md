# 架构与数据流

AllDayRec 是一个 Python 服务器加几个客户端。音频从录音设备或手机进来，服务器在本机做语音检测和声纹，语音识别用云端或本机引擎，摘要交给你配置的大模型，结果存进 SQLite，原始录音一直留在磁盘上。

## 组成部分

| 目录 | 内容 |
|---|---|
| `server/` | 服务端：上传队列、VAD 和声纹、语音识别引擎、对话、摘要、MCP（Python 3.11，uv） |
| `web/` | 网页：时间线、实时、人物、我的，以及对话、日历、待办、设备页（Vue，pnpm） |
| `app/` | iOS 和安卓手机 App：录手机麦克风或蓝牙录音设备、上传、固件升级（Flutter） |
| `firmware/devkit/` | nRF52840 板子的蓝牙录音设备固件（Zephyr / nRF Connect SDK），基于 Omi devkit |
| `firmware/selftest/`、`firmware/blerelay/` | 板子自检固件；测试用的 ESP32 蓝牙中继 |
| `hardware/lr-p3/` | LR-P3 录音设备的零件、接线和 3D 打印外壳 |
| `cli/` | `lr.py`：在终端或 Agent 里读你的对话 |

## 音频怎么进来

录音设备一直往 SD 卡里写，连着手机时把同一份记录同时推给手机；断开期间的部分，手机回来后从卡上读回来补齐。手机 App 把音频切成 Opus 短块上传到 `POST /api/chunks`；离线时块在手机上排队，之后再传。

服务器把每一块先存进磁盘，再按时间顺序交给这台设备的处理流程。所以一个断网很久的客户端回来后可以一次把积压全传上来，别的设备不受影响。能 POST 音频文件的东西都能当音源，这也是[导入已有录音](../how-to/import-recordings.md)的方式。

## 两层转写

服务器在本机用 FireRedVAD 找出哪里有人说话，然后分两层转写：

- **定稿层** 一直在跑。它在停顿处把音频切开，每段最长 5 分钟，每段只送一次给语音识别引擎（`ENGINE`），结果就是最终的转写。
- **初稿层** 只在有网页开着时跑。它在停顿处（一直没有停顿时每隔 `REFINE_EVERY_S` 秒）把新的音频送给 `DRAFT_ENGINE`，几秒内出字；`DRAFT_ENGINE=qwen-stream` 时改为把音频持续流式推给千问，边说边出字。初稿只在定稿还没覆盖的时间段显示，定稿到了就被替换。

文字和分句来自语音识别引擎；本机负责语音检测和说话人身份，各引擎的说话人从哪里来见下表。送给引擎之前，长于 3 秒的静音会被剪到 3 秒（`SQUEEZE_KEEP_S`）。

各引擎的说话人来源不同：

| `ENGINE` | 服务商 | 说话人 |
|---|---|---|
| `qwen` | 阿里云百炼，千问 Qwen-Audio 文件转写 | 引擎给出，再用本地声纹修正 |
| `volc` | 火山引擎豆包 Seed-ASR 2.0 | 本地声纹 |
| `stepfun-sse` | 阶跃星辰流式语音识别 | 本地声纹 |
| `stepfun`、`stepfun-file` | 阶跃星辰文件模式 | 引擎给出，再用本地声纹修正 |
| `local` | 服务器进程里的 sherpa-onnx X-ASR 中英模型，只出文字 | 本地声纹 |

本地引擎和云端引擎的准确率对比见[语音识别评测](./asr-benchmark.md)。

## 认人

声纹模型 ReDimNet2 在本机 CPU 上跑。服务器认得出「我」（录音者本人），在一段对话里把其他人分成 S1、S2…；太短、认不出来的句子标成 S?。你在网页上给某个标签起了名字，之后的对话里同一个声音就会被认出来。

## 计算接口

声纹、音乐检测和换人检测（pyannote，找一句话里换人的位置）是服务器里最重的三项计算，都放在同一个计算接口后面（`server/alldayrec/compute.py` 的 `Compute`）。接口只收 16 kHz 的 int16 采样，返回声纹向量、「是不是音乐」或一段 10 秒音频的逐帧说话人概率，不读数据库，不读音频文件，也不知道是哪个租户的数据。

- **默认在进程内计算**：不设 `INFER_URL` 时，服务器自己用 onnxruntime 算，和以前完全一样。
- **独立推理服务**：用同一个命令加参数启动的 `alldayrec --infer` 只提供这三项计算，可以部署在另一台机器上，比如有空闲 CPU 或 GPU 的机器。服务器设了 `INFER_URL` 和 `INFER_TOKEN` 后，把采样 POST 给它，自己不加载、也不下载这三个模型，服务器那台机器不用为它们花 CPU 和内存。推理服务停了、卡住了、回 401 或 403，或者返回的不是声纹、不是逐帧概率时，这次调用就等它恢复：2 秒后再试，然后 4 秒、8 秒，最长每 60 秒试一次，直到成功。这期间上传照常收音频、落盘、入库，网页照常能打开；只是这台设备的转写和说话人识别在排队，服务恢复后自动追上，一句不少。迟到区间（补传的旧录音）在服务失败期间不认领，重启后第一次核对 `/health` 没通过时也一样：服务器不先付这段的 ASR，也不用掉它的重试次数，只按退避时间去问 `/health`，通了才开始处理。已经在处理的区间等服务恢复，等的时间不算它的超时；这时停服会退回认领和这次的重试次数。同一个区间最多退回 3 次（每次认领都要重新付 ASR），只有服务在它处理时反复挂掉、又反复停服才会用完，之后按普通中断算，重试满 3 次标成 `failed`。声纹学习（改说话人以后学声纹、生成自己声音的卡片）也要等服务恢复。错误日志每分钟最多一条，`lr_infer_down_seconds` 给出服务已经失败了多久，可以用来告警。启动时服务器带令牌请求一次服务的 `/health`，核对模型文件和声纹维度；和服务器的不一致时，每次调用也照样等，日志里写明原因。

语音检测（VAD）、ffmpeg 解码和聚类认人留在服务器进程里。VAD 每台设备一路，要带着上一块的状态往下算，单次计算比一次网络往返还轻。解码读的是磁盘上的音频，聚类读的是这个租户的声纹库，这几项都必须和库、音频放在一起。部署：

```sh
# 推理机器上：模型文件和服务器的一样，缺的第一次启动时下载到 MODELS_DIR
INFER_TOKEN=<随机令牌> INFER_HOST=0.0.0.0 INFER_PORT=8771 alldayrec --infer
# 服务器的 .env：只经内网、Tailscale 或 HTTPS 反向代理访问它（不走环境变量里的代理）
INFER_URL=http://infer.example.com:8771
INFER_TOKEN=<同一个令牌>
```

`GET /health` 不需要令牌；`GET /metrics` 需要令牌，返回每项计算的调用次数、耗时和音频秒数。变量见[配置项](../reference/configuration.md#其他环境变量)。

一次请求最长 600 秒音频，换人检测（`/segment`）最长 10 秒，超过时服务回 413。413 说明是请求本身有问题，重试没有用，所以服务器不等也不重试：记一条错误日志，这次调用直接报错。

推理服务和服务器要同时升级到同一个版本。服务器要求 `/health` 里的模型文件和自己的完全一样，版本之间模型有变化（比如加了换人检测）时，先升哪一边都对不上，所有调用都会一直等，直到另一边也升级；这期间上传照常收，升级完以后自动追上。

## 录音存在哪里

`server/alldayrec/audio.py` 里所有对录音字节的读写都经过一个存储接口（`store.py`）：追加（只在本地）、按位置和长度读、整个写、是否存在、删除。每一块在 `pieces` 表里记着路径、位置和长度。默认 `STORAGE=local`，录音全在 `recordings` 目录里。`STORAGE=s3` 时，一个小时文件这样走完一生：

1. **开着（本地）**：这一小时的块照旧追加到本地的小时文件，fsync 之后、索引行提交之后才回复客户端。
2. **封存**：这一小时过去、又 `SEAL_IDLE_S`（默认 600）秒没有新块时，后台把整个文件上传成一个对象，核对大小和 SHA-256（PUT 时按内容的 SHA-256 签名，存储收到的字节不对会拒收），在一个事务里把这些块的路径改成对象（`s3:` 开头），然后才删本地文件。所以本地一般只有当前这一小时和正在封存的那一小时。
3. **迟到的块**（落在已封存的小时里）：先 fsync 到本地的暂存文件 `staging/<小时文件>.<代>`，建好索引就回复客户端。之后按小时成批合并：这一小时 `MERGE_IDLE_S`（默认 90）秒没再来迟到的块、暂存超过 `MERGE_MAX_BYTES`，或最早一块等了 `MERGE_MAX_S`（默认 1800）秒时，下载对象，把暂存的块按顺序接在后面，上传到同一个键，核对，在一个事务里改这些块的路径和位置，再删暂存文件。对象原有的字节一个不动，所以以前的每一行索引都还对；读旧版本的人读到的是同样的前缀。合并开始时代号加一，合并期间新来的块写进下一个暂存文件。
4. **读**：路径指向本地或暂存文件的块读本地文件；指向对象的块发一个带 Range 的 GET，只取这一块。读的时候文件刚好被封存或合并删掉了，就按最新的索引行再读一次。
5. **同一块又传了一份更长的**（按现在的规则保留更长的）：更长的那份照样追加（本地，或者小时已封存时进暂存文件），索引行换成它。
6. **导入的长文件**（超过 5 分钟的一块）：单独一个本地文件，马上整个上传成自己的对象，不合并。

崩溃也不丢：每次上传之前，`store_objects` 表先记下这个对象应有的大小、SHA-256 和要改的索引行。上传后、事务提交前崩溃了，重启时核对对象：和记的一致就只补做事务，不一致就重新上传。上传都是条件写入：新对象只在键还不存在时写，合并只覆盖封存时的版本（按 ETag），所以不会盖掉别的实例的对象。本地和暂存的字节要等对象核对无误、事务提交、而且没有索引行再指向它们以后才删；封存过的小时文件还要和对象的字节完全一样才删（中途改回过 `local`、又写进了新块的文件会留下）。同一个对象同一时刻只做一次封存或合并。对象存储连不上时上传不受影响，封存和合并退避重试，本地文件变多；已封存的录音读不到时播放返回 503，转写停在那一块等它恢复。

每个租户的对象在 `<S3_PREFIX><租户 id>/` 下面，这个前缀在租户第一次用时记进它自己的数据库，一个租户读写不到另一个的对象，合并进别的实例后也还是原来的前缀。监控指标：`lr_store_local_bytes`（还没封存的小时文件和暂存文件的字节数，不算改成 `s3` 之前的录音）、`lr_store_pending_seal`（到时间还没封存的文件数）、`lr_store_pending_merge`（有块在暂存的小时数）、`lr_store_errors_total{op}` 和 `lr_store_seconds_count{op}`、`lr_store_seconds_sum{op}`（对象存储每种调用和每次封存、合并的次数、失败次数和耗时）。`lr_store_pending_seal` 持续大于几个、或 `lr_store_local_bytes` 一直涨，说明对象存储出了问题，可以拿来告警。变量见[配置项](../reference/configuration.md)里的「可选：录音存进对象存储」。

## 对话、摘要和回顾

句子按时间归成对话：5 分钟没有人说话、录音设备停了，或者一段对话满 4 小时，它就结束。说话少于 10 秒的对话不保留成一段对话（句子还在转写里）。

只按时间分，商场、路上周围的人声会把几段互不相干的对话连成一段。所以较长的对话（`SPLIT_MIN_S`，默认 10 分钟）写摘要前，再让大模型按内容看一遍：从某处起换了人、换了事，而且那里确实停顿过，就从那里切成几段，各写各的摘要。切开的地方之后不会被迟到音频重新合并。

对话结束后，服务器用你配置的大模型写摘要：标题、摘要、每个人的要点、待办（带截止日期）、决定和标签。说话不到 60 秒的对话不调大模型，标题取第一句。每天 `RECAP_AT`（默认 10:00）写前一天的回顾。

「问 AI」用同一个大模型回答关于你过去的问题：最近几天的摘要放在提示词里，更早的或者更细的内容通过查询数据库的工具找到，每个说法都带出处对话的 id。

## 谁在读这些数据

网页、App 里的网页、[MCP 端点](../reference/mcp.md)和[命令行](../reference/cli.md)读的都是同一个租户的数据库。数据库是 SQLite，你也可以自己直接读，表结构见[数据目录](../reference/data.md)，表之间怎么关联、处理循环怎样推进见[领域模型](./domain-model.md)。

一台服务器可以服务好几个人，每个人一个 token、一个数据库和一个录音目录（`tenants.json`），在同一个进程里互相隔离。
